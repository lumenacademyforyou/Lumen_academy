### A2/A3 — bugs found and fixed along the way

Chasing the frontend journey test's failures surfaced four real, independent defects, all now fixed (confirmed via direct CDP protocol tracing that the app subsequently loads and paints correctly, and the fixed test's selectors match the real rendered markup):

1. **`npm run start` could not start at all.** `esbuild ... --format=cjs` bundled the generated Prisma client's `globalThis['__dirname'] = path.dirname(fileURLToPath(import.meta.url))` into a CJS module, where `import.meta.url` is `undefined` — the process crashed on line 1. Fixed by switching the backend bundle to ESM (`dist/server.mjs`; `package.json` already declares `"type": "module"`). Confirmed no code outside the generated client used CJS-only globals (`__dirname`/`require`).
2. **`npm run start` never set `NODE_ENV=production`**, so `server.ts`'s `if (config.nodeEnv === "production")` static-file-serving block never ran — the production entrypoint could never serve the built frontend at all. Fixed via the `cross-env` devDependency (named here per the directive's dependency-disclosure rule: needed because `NODE_ENV=production node ...` inline-env syntax isn't portable to this Windows/cmd.exe npm-script execution context).
3. **`server.ts`'s bare-root `app.get("/", ...)` JSON handler was registered unconditionally**, ahead of the production static-file block, so it shadowed `index.html` — `GET /` in production returned a JSON status stub instead of the actual app, every time. Moved it behind an `else` (only registered outside production).
4. **`router.use("/ai", aiRouter)` was registered before the explicit `POST /ai/study-plan` and `POST /ai/evaluate-attempt` routes**, and `aiRouter` blanket-applies `requireAuth` to everything under `/ai/*` — so those two routes, meant to stay public per their own comment ("still call Gemini directly... migrated separately"), were unreachable, always returning 401 first. Reordered so the public routes are matched before the auth-gated sub-router.
5. Also corrected a **port mismatch**: `playwright.config.ts` pointed at `localhost:3000`, but the server binds `config.port` (env `PORT`, defaulting to 4000, and `.env` sets 4000 explicitly) — nothing in this codebase ever used port 3000.

**Open item — not a defect, a local tooling limitation:** even after all of the above, the frontend browser test cannot be run to completion in this sandboxed dev shell. Direct CDP protocol tracing (`DEBUG=pw:protocol`) proved the page genuinely loads, paints (`firstPaint`/`firstMeaningfulPaintCandidate` fire), and behaves correctly (React Router's initial `historyApi` navigation completes) — but the Playwright *browser/page fixture setup* then stalls for nearly the entire configured test timeout before the test can proceed, regardless of how large that timeout is set (tried 30s/60s/90s — always fails with only ~5s left). Ruled out during investigation: GPU/compositing (tried `--disable-gpu`, SwiftShader), shared-memory limits (`--disable-dev-shm-usage`), sandboxing (`--no-sandbox`), and the full `chrome.exe` binary vs the default `chrome-headless-shell.exe` (full Chromium exits instantly in this sandbox and doesn't work here at all). This points to a characteristic of running Chromium browser automation inside this specific restricted shell, not an app or test-code defect. Bumped `playwright.config.ts`'s global timeout 30s → 60s as a reasonable CI safety margin regardless. **Action for a future session or the user:** re-run `npm run test:e2e` in a normal (non-sandboxed) shell or in actual CI to get a real pass/fail on this one spec — don't trust this sandbox's result for it.

## Phase E — Session management and auto logout
Status: done.

**Research first (Explore agent survey before writing anything):** auth is entirely Supabase-managed — `requireAuth.ts` only ever calls `supabaseAuth.auth.getUser(token)`; no self-signed JWT, no local session/revocation table, no idle-tracking anywhere in the stack (confirmed via grep across `backend/src` and `frontend/src`). One thing already existed and was directly reusable: `pauseAttempt`/`resumeAttempt` + `assess.attempt.server_deadline`/`paused_ms_total` + `envelope.ts`'s server-recomputed `remainingSeconds` (TE-P4/R-10) — fully built and tested server-side, just never called from the frontend. Phase E's real net-new work was the app-level idle/absolute-timeout policy layer Supabase has no concept of, plus wiring the frontend to the pause/resume primitive that already existed.

**Design decision (stated, not guessed):** the new `core.user_session` table is keyed by the Supabase JWT's own `session_id` claim (stable across access-token refresh within one login, changes only on a genuinely new sign-in) rather than by the access token itself or by `user_id` alone. This was chosen over the two obvious alternatives specifically to avoid two failure modes: keying by token hash would make every silent background token refresh look like a brand-new session (defeating both idle and absolute tracking); keying by `user_id` alone would mean two devices/tabs share one clock (one idle, one active) and — worse — would make a revoked/expired row silently self-heal on the very next request from a second, still-token-valid tab, which breaks E3's "an expired token must be rejected by the API, not merely hidden by the UI" requirement. `session_id`-keying avoids both: one row per login, each independently timed and revocable, and a revoked row never auto-resets — it stays revoked until a genuinely new Supabase sign-in mints a new `session_id`.

### Three real, previously-invisible defects F6 surfaced (all fixed, all reverified live)

Nobody could see any of these from code review, from the HTTP-level manual scripts (`verify-phase-d-http-flow.ts`, `verify-phase-e-session.ts` — both sign in via a real Supabase *server-side* client, which never touches the browser's CSP or the frontend's fake-login code path), or from unit/integration tests. Only a real browser, actually reaching the real page, could have found them — which is exactly why F6 is in the directive at all.

1. **Playwright's own `webServer` never actually ran the app in production mode.** `playwright.config.ts`'s `command: "npm run start"` relies on `cross-env NODE_ENV=production` to set the env var before `node dist/server.mjs` — this works fine when a person runs `npm run start` directly, but when *Playwright itself* spawned that command as its child process, `NODE_ENV` did not propagate through on this platform, so the server always fell back to `server.ts`'s non-production branch and `GET /` returned the bare JSON health stub instead of `index.html`. Every previous attempt at a frontend E2E journey was doomed at the very first "Sign In" lookup, regardless of selector correctness — this, not (only) sandboxed-Chromium stalling, is why it never worked before. Fixed by setting `NODE_ENV` directly via Playwright's own `webServer.env` option (`command: "node dist/server.mjs"`, `env: { NODE_ENV: "production" }`), bypassing cross-env/shell resolution entirely.
2. **The "Demo Account" quick-login button was completely non-functional as a real session.** `LandingView.tsx`'s modal `onClick={() => onLoginSuccess("Demo Student", false, false)}` set `isAuthenticated = true` in React state with **no Supabase call at all** — no real session ever existed. The very next authenticated call any real screen makes (`Header.tsx`'s own `GET /api/me` profile fetch) 401'd, and `apiFetch`'s existing generic 401 handler (`services/api.ts`) reacted exactly as designed for a *genuinely* expired session: signed out and hard-`window.location.assign("/")`'d back to the landing page — so this button silently bounced the user back to where they started within moments of "logging in." (The separate "Quick Demo" flow elsewhere on the page was unaffected — it already called the real `ensureDemoSession()`.) Fixed by making the modal's Demo Account button call `ensureDemoSession()` (the same real sign-in-or-create-once mechanism) before reporting success, with a loading state and real error surfacing via the existing `formError` UI. "Admin Login" right next to it was checked and is fine as-is — `AdminView.tsx` makes no API calls at all, so it never hits this failure mode.
3. **`helmet()`'s default Content-Security-Policy silently blocked every real cross-origin call this app legitimately makes.** Auth in this app is 100% client-side Supabase (no backend `/api/auth/login` exists — confirmed during Phase E's own survey) and published question images resolve to Supabase Storage public URLs (Phase B3) — both are cross-origin from the browser's perspective. `helmet()`'s zero-config defaults restrict `connect-src` and `img-src` to `'self'` only; the browser silently refused every `fetch()` to `https://<project>.supabase.co/auth/v1/*` with a CSP violation (no server-side error, no build warning — just a failed client-side fetch) and would have done the same to every Storage image URL. **This means real sign-in/sign-up has likely never worked against an actual production deployment of this app until this fix**, and neither would any image-bearing question. Fixed in `server.ts` by merging `helmet.contentSecurityPolicy.getDefaultDirectives()` with an explicit `connect-src`/`img-src` allowance for the app's own Supabase project origin (read from `config.supabaseUrl`), rather than disabling CSP outright.

### Two smaller, related fixes found in the same pass

- **A real race in Phase E's own reload-survival effect** (`App.tsx`'s `getActiveSession()` check): being async, it could resolve *after* the user had already manually launched a brand-new session (e.g. clicked "Start Practice" while the stale-attempt lookup was still in flight), silently clobbering the fresh session with an old one. Fixed with a `currentScreenRef` guard — the resumed session is only ever applied if the user is still on `"portal"` (hasn't navigated away on their own) at the moment the check resolves.
- **The shared demo account (`demo.student@lumenacademy.dev`) accumulates real, persistent `assess.attempt` rows** every time any manual script or E2E run signs into it — a `resolveActiveExam then createPracticeTest` cost, not a bug, but it means a leftover `in_progress` attempt from one run can get legitimately auto-resumed (and, if long-expired, auto-submitted) at the start of the *next* run, which looks like a failure if you're not expecting it. New `db/scripts/manual/cleanup-demo-account-attempts.ts` submits any stale `in_progress`/`paused` attempts for that account via the real state machine — run it before a fresh E2E pass if journeys start failing at "Proceed to Instructions" for no apparent reason.

### A real, measured performance finding — not fixed, flagged for a future session

`POST /api/assess/sessions` took **~14 seconds** against the live remote Supabase Postgres in one measured run (`db/scripts/manual/verify-phase-e-session.ts`'s sibling investigation while debugging F6's timeouts), and `GET /api/me` took ~5.8s in the same run. Root cause, read from the code rather than guessed: `createPracticeTest`/`startAttempt` insert **one row per served question via sequential awaited `pool.query` calls in a loop**, not a single batched multi-row insert — latency scales linearly with `pickCount` and each round trip pays the full network cost to the remote database. This is a real, user-facing severity (a student waiting 14+ seconds just to *start* a practice test) but batching those inserts is a nontrivial change to well-tested, R-9/R-10-invariant-bearing code (`attempt-flow.ts`) that wasn't in this phase's scope to rewrite under time pressure — `playwright.config.ts`'s `timeout` and the E2E spec's own per-step timeouts were widened to accommodate the real measured latency rather than papering over it with a shorter one that would just flake. **Flagging for a future session**: batch `assess.attempt_question`'s per-question inserts (and the equivalent in `assemble.ts`/`create-practice-test.ts` if any other per-row loops exist there) into a single multi-row `insert ... values (...), (...), ...` or a `unnest()`-based bulk insert.
