## A. Repetition and pool integrity

### A1 — No test-level uniqueness constraint; generic CRUD path can insert a duplicate across sections
**Severity:** P0
**Repro steps:** Call `testQuestionService.create()` (or any future route wired directly to `db/assess/test/test_section/test_question/test_question.repository.ts`'s `insertRow`) twice with the same `question_id` but two different `test_section_id`s belonging to the same `test_id`. Both inserts succeed — the only DB constraint (`uq_test_question_section_question`, `db/migrations/011_assess_scope.sql:66-67`) is scoped to `(test_section_id, question_id)`, not `(test_id, question_id)`.
**Root cause:** No `UNIQUE(test_id, question_id)` constraint exists anywhere in the schema (confirmed against all 27 migrations). The one path that guards against this (`ingestFixedPaper`, via its own `firstSeenAt` map in `db/assess/test/definition/ingest-paper.ts:73-93`) does so in application code, not the database, and only for that one entry point.
**Affected files:** `db/migrations/011_assess_scope.sql`, `db/assess/test/test_section/test_question/test_question.repository.ts`, `db/assess/test/definition/ingest-paper.ts`.
**Proposed fix:** Add a migration introducing `UNIQUE(test_id, question_id)` on `assess.test_question` (requires denormalizing `test_id` onto the row, or a trigger/CHECK against `test_section.test_id`, since `test_question` currently only carries `test_section_id`). Add the constraint as the actual backstop; keep `ingestFixedPaper`'s check for a clean error message before the DB rejects it.
**Blast radius:** Schema migration + one repository. No behavior change for `ingestFixedPaper` (already compliant); closes the gap for any other current or future write path.
**Fixed and shipped**: `db/migrations/027_test_question_cross_section_unique.sql` — denormalized `test_id` onto `assess.test_question`, backfilled and kept in sync by a `before insert or update of test_section_id` trigger (`assess.trg_test_question_set_test_id`), backed by `unique (test_id, question_id)` (`uq_test_question_test_id_question_id`). Applied and verified live against the dev DB: confirmed zero pre-existing cross-section duplicates before applying (would have blocked the migration, which is the correct failure mode — checked, not assumed); the constraint was then proven to actually reject a real cross-section duplicate insert via a rolled-back transaction against live data (no data changed). `TestQuestionModel` updated with the new column.

### A2 — Same question eligible under two concept nodes: mitigated within one generation call, unverified across independently-authored FIXED sections
**Severity:** P2 (downgraded from the lead's implied P0 — see reasoning)
**Finding:** Within one `assembleForAttempt` call, `globallyPicked` (the `$4::uuid[]` exclusion array threaded through `assemble.ts:129,186-204`) accumulates across blueprint lines, so a question matching two overlapping node scopes in two different lines of the *same* generation call cannot be drawn twice. **Not reproduced** for the BLUEPRINT-mode path.
**Residual risk:** For FIXED-mode papers authored by two independent calls to `ingestFixedPaper` (or the unguarded CRUD path from A1) targeting different sections that happen to reference the same underlying question tagged to two nodes, nothing outside A1's fix would catch it — this collapses into A1, not a separate mechanism.
**Affected files:** `db/assess/test/generation/assemble.ts`.
**Proposed fix:** No separate fix needed beyond A1; add a regression test asserting `globallyPicked` accumulation across ≥2 lines with overlapping node scope (belongs in TEST-CASES.md, Repetition bucket).
**Blast radius:** None (verification only).

### A3 — Group draw double-counting
**Severity:** N/A today — **must be built correctly when introduced**
**Finding:** No concept of a "question group" (comprehension passage, assertion-reason pair as linked rows, common-stem cluster) exists anywhere in the schema or `assemble.ts` (confirmed by exhaustive grep — no `group_id`/`question_group`/`cluster`/`passage_id` table or column). There is nothing today that could double-count or split a group, because there are no groups.

Whoever builds that must introduce the group concept for the first time and is at risk of exactly this bug (group counted as 1 toward section size but inserting N rows) on day one, since there's no prior implementation to copy.
**Affected files:** N/A now; will be `assemble.ts` + a new `content.question_group` (or similar) table when built.
**Proposed fix:** Track as a design requirement for the image-test-type fix, not a pre-existing bug to patch.
**Blast radius:** N/A.

### A4 — Concurrent generation: `assembleForAttempt` deadlocks the connection pool under concurrent load
**Severity:** P0
**Repro steps:** Fire ≥4 concurrent `POST /assess/sessions` (or `/attempts/start`) requests for BLUEPRINT-mode tests (subject-wise, unit, or full-mock — anything that goes through `assembleForAttempt`, i.e. everything except raw FIXED-paper attempts). Each `startAttempt` call holds one of the pool's 4 connections (`db/shared/pool.ts:18`, `max: 4`) via its own transaction (`attempt-flow.ts:135`), then calls `assembleForAttempt(testId, userId)` at `attempt-flow.ts:215`, which internally calls `pool.query(...)` three times (`assemble.ts:177,183,197`) needing an additional connection from the same exhausted pool. All four (and any beyond) hang forever.
**Root cause:** `assembleForAttempt` was never given the `client`-passthrough fix that `loadSectionSchemes` received for the identical bug (`attempt-flow.ts:65-76` documents that exact prior fix). `assembleForAttempt`'s signature is `(testId, userId, seed?)` — no client parameter.
**Affected files:** `db/assess/test/generation/assemble.ts`, `db/assess/test/attempt/attempt-flow.ts:215`.
**Proposed fix:** Give `assembleForAttempt` an optional `client` parameter (default `pool`, same pattern as `loadSectionSchemes`) and thread `startAttempt`'s transaction client through at the call site. Add a load test that fires ≥`pool.max` concurrent generations and asserts none hang past a timeout.
**Blast radius:** One function signature change + one call site. High-value, low-risk fix — matches an already-proven pattern in the same file.
**Fixed and shipped**: exactly the proposed fix — `assembleForAttempt(testId, userId, seed?, client = pool)`, threaded through at `attempt-flow.ts:215`. New test `db/assess/test/attempt/concurrent-generation.test.ts` fires 4 concurrent BLUEPRINT-mode `startAttempt` calls (`== pool.max`) across 4 different users and asserts all complete within a bounded time — run live against the dev DB twice in a row, both green. Did not attempt to reproduce the pre-fix hang live (reverting and re-running risks genuinely tying up a shared dev database's connections indefinitely, which is the whole point of the bug) — confidence instead comes from this being the identical shape of an already-proven fix (`loadSectionSchemes`) in the same file.

### A4b — TOCTOU race on "one active attempt per user" (new finding, not in the prompt's lead list)
**Severity:** P1
**Repro steps:** Fire two concurrent `startAttempt` calls for the same user (two tabs, or a client retry racing the original request). Both read `activeRes.rowCount === 0` (`attempt-flow.ts:127-133`) before either has committed an insert, since this check runs on a plain `pool.query` *before* `pool.connect()`/`begin` (line 135) — no advisory lock, no transaction isolation covers it.
**Root cause:** The active-attempt guard is a read-then-act check with a window between the read and the eventual write that isn't closed by any lock.
**Affected files:** `db/assess/test/attempt/attempt-flow.ts:126-137`.
**Proposed fix:** Take a Postgres advisory lock keyed on `user_id` (`pg_advisory_xact_lock(hashtext(user_id))`) at the start of the transaction, before the active-attempt check, so a second concurrent call blocks until the first commits/rolls back and then sees the real post-commit state. Cheaper than a new unique index and doesn't require a schema change.
**Blast radius:** One function; advisory locks release automatically on transaction end, no cleanup needed.
**Fixed and shipped**: exactly the proposed fix — the active-attempt check moved inside `startAttempt`'s transaction, gated by `pg_advisory_xact_lock(hashtext(user_id::text))` taken first. `concurrent-generation.test.ts`'s second sub-test fires 2 concurrent `startAttempt` calls for the same user and asserts exactly 1 succeeds, the other rejects `ActiveAttemptExistsError`, and a direct DB count confirms only 1 active attempt row exists afterward — run live against the dev DB, passing.

### A6 — Anti-repeat window compares against scored attempts only; an abandoned attempt burns nothing
**Severity:** P1
**Repro steps:** Start a test (creates `assess.attempt_question` rows for 45 questions), never submit it (abandon it, or let it sit `in_progress`/`paused` indefinitely — see C1/C3). Generate a new test for the same user/scope. All 45 previously-served questions are still fully eligible and unweighted-as-seen, because `assess.user_question_seen` is only written inside `submitAttempt` (`attempt-flow.ts:714-724`), never at serve time (`startAttempt`) or on any intermediate state.
**Root cause:** The exposure ledger is updated at score time, not serve time — by design for computing `was_correct_last`, but with the side effect that an attempt that's started and abandoned (deliberately, or via any of the resume/lockdown gaps in §B/§C) never marks its questions as seen.
**Second half of the lead ("burns questions the user never saw") — not reproduced:** `submitAttempt`'s loop over `evaluatedById` (`attempt-flow.ts:714`) covers every served question including unattempted ones (evaluated with an `UNATTEMPTED` outcome), so a submitted attempt correctly marks all served questions as seen, attempted or not. This half of A6 does not occur.
**Affected files:** `db/assess/test/attempt/attempt-flow.ts` (`startAttempt`, `submitAttempt`).
**Proposed fix:** Write a provisional `user_question_seen` row (or a separate `attempt_question`-scoped "served" marker, which already exists as the PK on `assess.attempt_question`) at serve time, and have the anti-repeat sort/exclusion logic in `assemble.ts` consult *served* questions (via `attempt_question` joined across all of a user's attempts, not just `user_question_seen`) rather than only scored ones. This also naturally fixes C1 (paused vs. abandoned) if tied to the same abandonment/expiry policy.
**Blast radius:** Touches the candidate-pool query (`LINE_CANDIDATE_SQL`) and `startAttempt`'s insert path — needs care to keep both mid-attempt "which questions am I already seeing in *this* paper" exclusion (`globallyPicked`) and cross-attempt "have I seen this before" exposure separate, since they serve different purposes.
**Fixed and shipped**: `startAttempt` (`attempt-flow.ts`) now upserts `assess.user_question_seen` for every served question immediately after the `attempt_question` bulk insert, in the same transaction — `last_seen_attempt_seq=0`/`was_correct_last=null` as an explicit "served but not yet scored" placeholder, incrementing `times_seen` and `last_seen_at`. `submitAttempt`'s own write no longer increments `times_seen` (it would otherwise double-count every submitted question relative to an abandoned one) — it now only fills in the real `was_correct_last`/`last_seen_attempt_seq` once scoring is known. **Real, load-bearing side effect found and documented, not glossed over**: this directly breaks A10's naive "reproduce a past draw" premise, since marking exposure at serve time changes the very sort key the candidate query used to produce that draw in the first place — see A10's own updated entry. Verified live: a started-then-abandoned attempt's questions now show up in `assess.user_question_seen` with `times_seen >= 1` immediately, before any submit call; a submitted attempt's `times_seen` was confirmed identical before and after submit (no double count).

### A7 — Duplicates at source (same question imported twice with different IDs)
**Severity:** P1 (data quality, not code)
**Finding:** Confirmed structurally possible — `content.question` has no normalized-stem uniqueness constraint, and nothing in the import path (`db/scripts/import/import-content.ts`, per the image-audit pass) checks for a near-duplicate stem before insert. This is exactly what §5's R2 duplicate-detection SQL (5.1-5.3 in the prompt) is for.
**Proposed fix:** Not a code fix — a data remediation task. Run R2 (§5 of the prompt) against the live pool once schema/column names are confirmed against the real `content.question`/`content.question_option` (the prompt's own SQL is "best-guess," needs correcting first), then apply the stated dedup policy (retire, `status='DUPLICATE'`, `duplicate_of` pointer — never hard-delete, since attempts reference these IDs). Tracked as its own report deliverable, not folded into the code-fix phase.
**Blast radius:** Data-only if done via the retire policy; do not delete rows with existing attempt references.

### A8 — Shuffling applied after the uniqueness check
**Severity:** Not reproduced
**Finding:** For questions, the `WHERE ... not (question_id = any($4))` exclusion runs before the `ORDER BY md5(...) LIMIT` shuffle (`assemble.ts:129` vs `141-145`) — correct order. For options, there is no shuffle step at all (see A9's related finding) so the ordering question doesn't apply.
**Proposed fix:** None needed for questions. See A9 for the option-shuffle gap itself.

### A9 — Random selection with replacement / option shuffling
**Severity:** P2 (schema-supported feature never implemented, not a correctness bug per se)
**Finding:** No `ORDER BY random()` anywhere in `db/` (confirmed by exhaustive grep) — question selection uses a seeded `md5(question_id || seed)` sort, which is safe. **However, options are never shuffled at all** despite two dead schema columns suggesting the feature was intended: `assess.test_question.shuffle_seed` (`004_assess.sql:76`) and `assess.attempt_question.option_order` (`020_attempt_question.sql:21`) are never read or written anywhere in `db/`. Options are always served in static `display_order` (`envelope.ts:136-144`).
**Root cause:** Feature was scaffolded (schema columns added) but never wired into `assemble.ts`/`attempt-flow.ts`.
**Affected files:** `db/assess/test/generation/assemble.ts`, `db/assess/test/attempt/attempt-flow.ts`, `db/assess/test/attempt/envelope.ts`.
**Proposed fix:** Out of this pass's stated scope unless the product wants option shuffling — flagging as a real gap between schema intent and implementation, not fixing unilaterally. If the product does want it: generate `option_order` once at `startAttempt` (persist per attempt, never per render — same discipline as question selection), and score off `option_id`, never position (already true per the audit — scoring already keys on `option_id`, so shuffling can be added without touching scoring logic).
**Blast radius:** If implemented: `startAttempt` insert path + envelope's option-serialization order. Deferred — needs a product decision, not assumed.

### A10 — Generation seed captured but never reused (new finding)
**Severity:** P2
**Finding:** `assembleForAttempt`'s optional `seed` parameter is never supplied by its only caller (`attempt-flow.ts:215` calls it with 2 args, no seed) — a fresh random seed is generated every time (`assemble.ts:35-42`) and persisted to `assess.attempt.generation_seed` (`attempt-flow.ts:216`), but nothing ever reads that column back to reproduce a past draw.
**Root cause:** Plumbing exists (seed parameter, seed persistence) but the "regenerate this exact paper for dispute resolution / debugging" capability was never built on top of it.
**Affected files:** `db/assess/test/attempt/attempt-flow.ts`.
**Proposed fix:** Add an admin/debug function that re-runs `assembleForAttempt(testId, userId, storedSeed)` against `attempt.generation_seed` for after-the-fact verification. Not required for the fix phase's own done-when criteria, but directly enables the "generator takes an optional seed and is deterministic under it" non-negotiable (§4 of the prompt) to actually be exercised in anger.
**Blast radius:** New read-only utility function; no change to the write path.
**Fixed and shipped**: `reproduceAttemptAssembly` (`attempt-flow.ts`). **Real limitation found live while writing its test, not theoretical:** A6's own fix (this same document) marks a served question "seen" in `assess.user_question_seen` at serve time, and the candidate query sorts unseen-before-seen — so the act of starting the original attempt changes the very exposure state its own candidate query depends on. A call to `reproduceAttemptAssembly` any time after the attempt exists will generally **not** reproduce the identical question set once any served question was previously unseen, because "unseen" is no longer true by the time you reproduce it. Confirmed live: a direct attempt at reproduction returned a completely different question set from the original. What remains genuinely true and is what the test now actually asserts: `assembleForAttempt` is deterministic given an identical seed and *unchanged* exposure state between two calls (proven by calling it twice with an explicit seed and no attempt started in between). Documented prominently on the function itself and in its test file — A10's fix is real and useful as a "what would this seed draw today" sanity check, but is not the byte-for-byte audit trail its original framing implied once A6 is also in place. This is a genuine interaction between two fixes in this same pass, not a regression in either one individually.

## B. Session lockdown

**Overall finding: there is currently no session-lockdown mechanism in this app at all, client or server, beyond the exam timer.** Every one of B1-B10 below is confirmed absent rather than partially implemented, with one partial exception (B4/B9's autosave-only visibility handling). This is the single largest gap against the prompt's Hard Rule #4.

### B1 — Browser back/forward escapes the player
**Severity:** P0. **Repro:** during an attempt, press browser Back. **Root cause:** no `popstate` listener anywhere in `frontend/src` (confirmed absent by grep); `currentScreen` routing in `App.tsx` is plain React state with no History API integration at all — there's nothing for Back to even "escape," because forward/back navigation was never wired to app screens in the first place, meaning Back likely does nothing or navigates the whole tab away depending on browser history state. **Fix:** push a history entry on entering `test_taking` and listen for `popstate`, re-pushing/blocking with a confirm-or-redirect-to-pause behavior (see B7's shared design). **Affected files:** `frontend/src/App.tsx`, `frontend/src/pages/TestTakingView.tsx`.
**Fixed and shipped**: confirmed live that no history entry is ever pushed for the system_check/lobby/test_taking flow (none of `handleStartTest`/`handleSessionCreated`/etc. in `App.tsx` call `navigate()`), so the history stack at the moment a student is mid-test is whatever it was *before* they started — the first Back press has nothing exam-related to land on and pops straight past the app, a real escape rather than a same-document `currentScreen` change this component's existing full-screen-override rendering could otherwise absorb. `TestTakingView.tsx` now pushes a throwaway `history` entry on mount and listens for `popstate`: on fire, it re-pushes the same entry (neutralizing the browser's default navigation) and routes through the exact same `handleExitAndPause` confirm-and-pause flow the "Exit & Pause" button already uses (guarded by the existing `exitingLifecycleRef` so a stray popstate during an already-in-flight submit/exit doesn't double-prompt). New Vitest cases in `TestTakingView.test.tsx` dispatch real `PopStateEvent`s and assert both the history re-push and the confirm→pause→onCancel chain fire, plus that an already-exiting attempt doesn't re-prompt; both stable.

### B2 — Direct URL entry to another route while `IN_PROGRESS` succeeds
**Severity:** P0. **Repro:** with an attempt in progress, manipulate `currentScreen` state (or, once real routes exist, type a URL). **Root cause:** `currentScreen` is unguarded local state; no route guard checks for an active attempt before rendering a different screen. **Fix:** a single guard in `App.tsx`'s screen-transition function: if an attempt is active and the target screen isn't `test_taking`/an explicit exit flow, block or redirect to the pause-confirmation path. **Affected files:** `frontend/src/App.tsx`.
**Re-audited rather than fixed as originally scoped**: tracing `App.tsx` live shows `currentScreen === "test_taking" && activeSession` fully overrides the render tree (no `Header`/nav/other screens mount alongside it), and every `setCurrentScreen` call lives inside `App.tsx` itself — nothing mounted during `test_taking` ever calls `navigate()`, so there is no in-SPA click path that can "render a different screen" out from under an active attempt; a same-document `popstate` (Back/Forward) is the only real vector, and that's B1's fix, which this now shares. The one remaining vector — a full browser navigation (URL bar retype) — causes a real page reload, which the app's existing E1/E4 reload-survival flow already catches: a fresh load with an in-progress attempt surfaces the non-dismissible (`closeOnBackdropClick={false}`, `closeOnEscape={false}`) Resume/Submit-now modal before anything else is interactive, and B8's server-side `423 ATTEMPT_LOCKDOWN_ACTIVE` allowlist independently blocks any other endpoint from returning real data even if the UI briefly renders behind it. No separate code change needed beyond B1.

### B3 — Refresh (F5) does not lose answers server-side, but the UI cannot show that
**Severity:** P0 (perceived data loss — collapses into C4, tracked jointly). **Repro:** answer several questions, refresh, land back in `test_taking`. **Root cause:** the envelope correctly returns the same attempt with all persisted responses, but `TestTakingView`'s `selectedAnswers`/`flaggedQuestions`/`currentIndex`/`questionTimeMap` state all initialize empty/zero and are never seeded from `session.responses` (see C4 for the full citation). **Not** "starts a fresh attempt" (the lead's other reading) — confirmed the same `attempt_id` and deadline are preserved; the bug is purely a client rehydration gap.

### B4 — Tab switch / blur / minimize is not detected for integrity purposes (only for autosave)
**Severity:** P1. **Finding:** `visibilitychange` **is** wired (`TestTakingView.tsx:146-156`), but its only effect is `flushDirty()` — a background autosave trigger. Nothing writes an `attempt_event` row or any other record of the blur for later integrity review (confirmed: `attempt_event` schema exists at `db/assess/test/attempt/attempt_event/`, but grepping its writers shows no call from the visibility handler). **Fix:** call the existing `attempt_event` write path (already used elsewhere in the attempt lifecycle) from the visibility handler with an event type like `tab_hidden`/`tab_visible`, timestamped, so a report can later show "student left the tab N times for M seconds total." **Affected files:** `frontend/src/pages/TestTakingView.tsx`, `db/assess/test/attempt/attempt_event/attempt_event.service.ts`.
**Fixed and shipped**: `event_type` on `assess.attempt_event` is unconstrained free text (confirmed via `012_domain_checks.sql`'s own comment — no migration needed), and the existing `POST /assess/attempts/:id/events` route already accepted arbitrary `event_type`/`event_payload`, just never called from the frontend. Added `postAttemptEvent()` (`frontend/src/services/sessionApi.ts`) and wired it into the existing visibility handler: `tab_hidden` logged on hide, `tab_visible` with `{hiddenForMs}` logged on return — both best-effort/fire-and-forget so a failed log never blocks the student. New Vitest case in `TestTakingView.test.tsx` dispatches real `visibilitychange` events and asserts both calls fire with the right payload; passing, stable across repeated runs. (Along the way, found and fixed a real test-infra bug this uncovered: `vi.restoreAllMocks()` in the suite's `afterEach` was silently clearing the `mockResolvedValue` configured at `vi.mock()` factory time for every subsequent test, not just call-history — any component code chaining `.catch()` directly on such a call would throw synchronously once that happened. Fixed by re-establishing the resolved-value config in `beforeEach` instead of only at module load.)

### B5 — Second tab opens the same attempt; tabs race on save
**Severity:** P1. **Finding:** nothing prevents two tabs from both loading the same attempt's envelope and both autosaving independently — last-write-wins per question (keyed by `question_id`, so concurrent answers to *different* questions are safe, but concurrent edits to the *same* question from two tabs silently overwrite each other with no conflict signal). Compounds with A4b (no lock on attempt creation) but is really a separate steady-state race once an attempt already exists. **Fix:** out of scope to fully solve (would need optimistic concurrency / a version column on `attempt_response`), but at minimum surface a "this test is open in another tab" warning via a `BroadcastChannel`/`localStorage` heartbeat — cheap, client-only, and directly addresses the reported symptom without a schema change.
**Fixed and shipped, scoped exactly as proposed**: `TestTakingView.tsx` opens a `BroadcastChannel` scoped to `lumen_attempt_${attemptId}` on mount, announces itself with a random per-instance `tabId`, and any other tab for the same attempt (an `announce` or `ack` from a different `tabId`) flips a banner on in both tabs — a non-blocking amber bar above the header, not a hard block, since the actual autosave behavior (last-write-wins per question) is unchanged and still safe for different questions. No schema change, no server involvement. New Vitest case posts a message on a second `BroadcastChannel` instance for the same attempt id and asserts the banner appears.

### B6 — Fullscreen exit is not handled (because fullscreen is never entered)
**Severity:** P1. **Finding:** confirmed absent — no `requestFullscreen`/`fullscreenchange` reference anywhere in `frontend/src`. There is nothing to "exit" because the test never requests fullscreen in the first place; the lead as stated ("user simply leaves fullscreen and browses") presumes a fullscreen mode that doesn't exist yet. **Fix:** request fullscreen on test start (`Element.requestFullscreen()`), listen for `fullscreenchange`, and on exit show a non-dismissible "return to fullscreen to continue" overlay that blocks interaction with the question but does *not* auto-submit (per the debug plan's own explicit prior guidance not to punish accidental keypresses — same policy should carry over here). **Affected files:** `frontend/src/pages/TestTakingView.tsx`.
**Fixed and shipped, with a real cross-browser gap found and guarded against, not assumed away**: the request itself has to fire from `LobbyView.tsx`'s "I Understand, Start Test" click (`handleContinue`) — the one genuine synchronous user gesture in the whole flow; the 30s countdown that actually calls `onStartTest()` fires from a `setInterval`, and `TestTakingView` itself mounts off a `React.lazy()` chunk fetch, neither of which carries the transient activation `requestFullscreen()` requires by spec. `TestTakingView.tsx` then only tracks `fullscreenchange` state and shows a non-dismissible, non-punitive (no auto-submit) "Return to Fullscreen" overlay whenever fullscreen isn't active, with its own button as a second real-click fallback (covers both an exit mid-test and the lobby's request having been silently rejected). **Found live while writing this, not anticipated going in**: the Fullscreen API is entirely unsupported on iOS Safari/Chrome (no `Element.requestFullscreen` at all, ever) — shipping the overlay unconditionally would have permanently locked the exam behind an overlay that could never clear on every iPhone, a strictly worse regression than the original gap. Feature-detected (`document.fullscreenEnabled` + `typeof requestFullscreen === "function"`) and the whole mechanism is skipped where unsupported. New Vitest cases cover both paths: overlay blocks and clears correctly when the API is mocked as supported, and never appears at all when it's mocked as absent.

### B7 — No `beforeunload` guard, and no server-side equivalent
**Severity:** P0. **Finding:** confirmed zero occurrences of `beforeunload` anywhere in `frontend/src`. **Fix:** add a `beforeunload` handler that shows the browser's native confirm prompt while an attempt is `in_progress`, in addition to (not instead of) the existing `pagehide` autosave flush. The "server-side equivalent" the lead asks for doesn't map onto `beforeunload` literally (a client-only event can't have a server twin) — the real server-side equivalent is B4's missing `tab_hidden` event plus the existing autosave, which already ensures no answer is lost even if the browser closes; the gap this bug is really about is the *confirmation prompt*, which is unavoidably client-only.
**Fixed and shipped**: a `beforeunload` listener in `TestTakingView.tsx` calls `preventDefault()`/sets `returnValue` unconditionally while mounted, guarded by an `exitingLifecycleRef` flag set `true` right before the two legitimate exit paths (`handleSubmitAnyway` on successful submit, `handleExitAndPause`'s `finally`) so a genuine, intentional exit never triggers a spurious native prompt. New Vitest cases: one confirms the prompt fires (dispatch a cancelable `beforeunload`, assert `defaultPrevented`) while an attempt is active; another confirms it does **not** fire once the attempt has auto-submitted (reusing the existing, already-reliable "auto-submit at zero time remaining" flow rather than clicking through the submit-confirmation modal, which proved timing-flaky under fake timers — same lesson as C4's own test design). Both stable across repeated runs.

### B8 — Server accepts non-test API calls during an active attempt
**Severity:** P1. **Finding:** confirmed by construction — the only server-side guards found anywhere for `attempt_state === 'in_progress'` are on the attempt/response/submit endpoints themselves (§1.3 of AUDIT.md). Nothing blocks calling `GET /dashboard/analytics`, `GET /catalog/tree`, `GET /me`, or any other unrelated endpoint while an attempt is active — these all remain fully callable. **Product question, not purely technical:** deciding *which* non-test endpoints should be blocked during an active attempt (all of them? just content-browsing ones?) needs a policy call before implementing a blanket "no other API calls during an attempt" server-side gate, since some (e.g. `/me` for session refresh) are needed for the test screen itself to keep working. **Proposed fix:** introduce an explicit allowlist (not blocklist) of endpoints permitted during `IN_PROGRESS` — attempt/response/submit/pause/session-refresh — and reject everything else with a clear `ATTEMPT_LOCKDOWN_ACTIVE` error, enforced via middleware that checks for the user's active attempt once per request (cacheable, cheap).
**Fixed and shipped, policy decision made explicitly rather than left open**: confirmed live (grepped `frontend/src`) that `TestTakingView` — the only screen mounted while an attempt is `in_progress`, since it already renders standalone outside the Header/app shell (BUG-09) — only ever calls `/assess/attempts/:id/*` endpoints; nothing else is legitimately needed during a test, including `/me` (session refresh happens via the Supabase SDK directly against Supabase, not this backend). So the allowlist is scoped tightly: `/api/assess/attempts/*`, `/api/auth/session/*` (idle/absolute session-timeout checks, unrelated to test content), and `/api/health`. Everything else returns `423 ATTEMPT_LOCKDOWN_ACTIVE` for a user with an `in_progress` attempt. **Deliberately scoped to `in_progress` only, not `paused`** — pausing (Exit & Pause) is this app's own sanctioned "leave and browse elsewhere" mechanism; locking down navigation for a paused attempt would break that flow rather than protect anything. New `backend/src/middleware/attemptLockdown.ts`, folded into `requireAuth.ts` itself (the one place every authenticated route in the app already passes through) rather than added piecemeal to the half-dozen routers that call `requireAuth` in inconsistent per-route/router-wide patterns — a targeted grep confirmed this reaches catalog/content/core/learn/admin/api.ts uniformly with one change, not five. Fails open on a DB error (never blocks the whole app on a failed lockdown check), matching the codebase's existing best-effort-guard discipline elsewhere. **Verified live against a real running server** (`npm run dev:api`), not just reasoned about: `db/scripts/manual/verify-b8-attempt-lockdown.ts` signs in as the real demo account, confirms `/analytics/dashboard` is reachable with no active attempt (200), starts a real session, confirms `/analytics/dashboard` now returns 423 and `/me` also returns 423 (not allowlisted) while the attempt's own `/envelope` and `/submit` stay reachable (200), then confirms `/analytics/dashboard` is reachable again (200) once the attempt is scored — full pass, all assertions correct. Dev server stopped and port 4000 confirmed clear afterward. Full regression suite (82 backend + 39 frontend) re-run clean after this change.

### B9 — Mobile: notification pull-down / incoming call / background kill

## C. Pause, resume, and abnormal exit

### C1 — No distinction between paused (recoverable) and abandoned (past grace window)
**Severity:** P1
**Finding:** Confirmed — the DB CHECK constraint allows `'abandoned'` (`018_test_engine.sql:111-113`) but **no live code path ever writes it** (only test fixtures do). An attempt that a student walks away from indefinitely sits in `in_progress`/`paused` forever unless one of the three lazy-reconciliation triggers fires (`getEnvelope`, `listOwnAttempts`, `startAttempt`), at which point `enforceExpiry` moves it straight to `scored` (via `expiry.ts`) if its deadline has passed — there is no intermediate "abandoned" grace-window state at all, just "still open" or "expired-and-scored."
**Root cause:** The state machine was designed with `abandoned` as a schema-legal value but the policy for *when* something transitions there (and what distinguishes it from a normal timer-based `scored`-via-expiry) was never implemented.
**Affected files:** `db/assess/test/attempt/expiry.ts`, `db/migrations/018_test_engine.sql`.
**Proposed fix:** Define a grace window (e.g. no activity — no response write, no heartbeat — for N hours past `server_deadline`, or immediately past deadline with zero responses at all) that routes to `abandoned` instead of `scored` when there's nothing to score; keep `scored` for anything with ≥1 response at expiry. This also directly feeds A6's fix (an `abandoned` attempt's questions should probably still count as "served," even if the attempt itself isn't scored).
**Blast radius:** `expiry.ts`'s `enforceExpiry` function; a decision needed on whether `abandoned` attempts get a scorecard at all (recommend: no scorecard, but questions still marked served per A6).
**Fixed and shipped, policy decision made explicitly rather than left open**: went with the simpler of the two proposed rules — **immediately past deadline with zero saved responses routes to `abandoned`; anything with ≥1 `assess.attempt_response` row, however partial, still goes through the unchanged `scored` path** — rather than also inventing a separate N-hours-of-inactivity threshold for non-empty attempts, which would need a real product number this pass has no source for (same reasoning D1's NTA weightage work was deferred over, not guessed at). New `abandonAttempt` (`attempt-flow.ts`) does the actual transition — re-checks the response count itself inside the same row lock rather than trusting a caller's earlier read (a response landing in the gap between the caller's check and the lock must never be silently dropped; falls through to the real `submitAttempt` scoring path instead if that happens) and is idempotent against an already-terminal attempt, same D-7 reasoning as `submitAttempt`'s own already-scored short-circuit. `expiry.ts`'s `enforceExpiry` and `sweepExpiredAttempts` both now check the response count first and call `abandonAttempt` or the unchanged `submitAttempt` accordingly (extracted into a shared `closeExpiredAttempt` helper so the two lazy/eager call sites can't drift). No migration needed — `abandoned` was already schema-legal (018_test_engine.sql) and the frontend (`MyResultsView.tsx`'s `STATE_LABEL`/`STATE_BADGE_CLASS` maps, and its `canOpen = attemptState === "scored"` gate disabling View/Download with an "Available once scored" tooltip) was already built anticipating exactly this value, just never received it live — confirmed by grep before assuming any frontend work was needed. `submitted_reason` reuses the existing `'expiry'`/`'sweeper'` values (no new CHECK-constraint value needed — that column is independent of `attempt_state`). Updated `db/assess/test/attempt/expiry-sweeper.test.ts` (its existing never-answered scenario is exactly this bug's target case — assertions changed from expecting `scored` to `abandoned`) and added a new sub-test proving an attempt with one real saved response still scores normally; also fixed `db/scripts/manual/prove-te-p4-expiry-verify.ts`, an older manual proof script whose hardcoded `scored` assertions were now factually stale for its own never-answered scenario. **Verified live**: `npx tsc --noEmit` clean; the full `expiry-sweeper.test.ts` file (5 sub-tests, including the two new/changed ones) run directly against the dev DB, all passing; full suite 83/83 node:test + 44/44 Vitest; production build clean.

### C2 — Timer state on resume
**Severity:** Not reproduced — confirmed correct.
**Finding:** `envelope.ts:107-108` recomputes `remainingSeconds` from `server_deadline + paused_ms_total` against the current server time on every read — never trusts a client-submitted value. This is already the correct, server-authoritative design the prompt asks for.
**Caveat:** as noted in AUDIT.md §1.3, `server_deadline`/`paused_ms_total` are among the columns writable through the unguarded generic `PATCH /:attemptId` route (see D-below/the session-flow finding) — the computation is correct, but its inputs aren't protected from tampering by the attempt's own owner. **This is really the same bug as the CRUD-bypass finding below, not a separate timer bug.**

### C3 — Timer expiry while the client is offline: no sweeper exists
**Severity:** P0
**Repro steps:** Start an attempt, go offline (or just close the tab) before the deadline, and never reopen the app (or reopen only after the deadline, without ever hitting `/envelope`, `/attempts` list, or starting a new test — none of which is guaranteed to happen soon).
**Root cause:** `db/scripts/sweep-expired-attempts.ts` is a standalone script explicitly documented in its own header as not wired to any scheduler ("no queue or cron infrastructure is wired up here... run manually or by a platform scheduler later") — confirmed via grep across all `*.json`/`*.yml`/`*.yaml` config that it is invoked nowhere automatically. The only enforcement is the three lazy, on-read reconciliation call sites.
**Affected files:** `db/scripts/sweep-expired-attempts.ts`, deployment/process config (none currently references it).
**Proposed fix:** Wire the existing script into an actual scheduler (a `node-cron`/`setInterval` process inside the server, or a real platform cron if the hosting supports it) running every N minutes, calling the same `enforceExpiry`/reconciliation logic already proven correct by the lazy paths. This is the single highest-value fix in this section — the script already exists and is already correct, it's purely a wiring gap.
**Blast radius:** New process/scheduled job; no logic changes needed to the sweep script itself (verify it reuses `expiry.ts`'s functions rather than duplicating logic — confirm at fix time).
**Fixed and shipped**: extracted the sweep query into a shared `sweepExpiredAttempts()` (`expiry.ts`), used by both the manual script (`sweep-expired-attempts.ts`, now a thin wrapper) and a new `backend/src/jobs/expirySweeper.ts` running it on a plain 60s `setInterval` inside the live server process (started in `server.ts` on boot, stopped in its existing graceful-shutdown handler). New integration test `expiry-sweeper.test.ts` simulates the exact Definition-of-Done scenario literally — starts an attempt, never calls any of the lazy-reconciliation trigger points (`getEnvelope`/`listOwnAttempts`/`startAttempt`) again for it, force-sets its deadline into the past via direct SQL, then calls `sweepExpiredAttempts()` and confirms the attempt is force-closed with `submitted_reason='sweeper'`; also confirms a not-yet-expired attempt is left untouched and that re-running the sweep is a no-op. All three assertions verified live against the dev DB.

### C4 — Resume does not restore answered options, flags, index, or per-question time
**Severity:** P0
**Repro steps:** Answer 5 questions, flag 2 for review, navigate to question 8, refresh the page (or trigger any resume path). Land back on question 1, nothing answered, nothing flagged.
**Root cause:** confirmed field-by-field — `TestTakingView.tsx:73-76` initializes `selectedAnswers`, `flaggedQuestions`, `currentIndex`, and `questionTimeMap` to empty/zero with no effect that reads `session.responses` (already returned by the envelope, `envelope.ts:252-258`) to seed any of them. Per-question time isn't even in the envelope response shape at all (`EnvelopeResponse` has no time field), so it isn't restorable without also extending the envelope.
**Affected files:** `frontend/src/pages/TestTakingView.tsx`, `db/assess/test/attempt/envelope.ts` (for the time-spent field).
**Proposed fix:** On mount (or whenever `session`/`attemptId` changes), seed `selectedAnswers`/`flaggedQuestions` from `session.responses`; seed `currentIndex` to the first unanswered question (or persist+restore an explicit `current_question_index`, which the prompt's own attempt model calls for — currently absent from the schema entirely, would need a migration). Add a `timeSpentSeconds` field to `EnvelopeResponse` sourced from `attempt_response.time_spent_seconds` so `questionTimeMap` can be seeded too.
**Blast radius:** Frontend-only for answers/flags (uses data already sent). Current-index restoration needs a schema decision (new column vs. derive-from-first-unanswered); time restoration needs one additive envelope field. This is the highest-value single fix in the whole audit for perceived reliability — directly satisfies the prompt's Definition of Done checkbox "Kill the browser mid-test → resume restores answers, flags, index, and correct remaining time."
**Fixed and shipped**: went with derive-from-first-unanswered rather than a new persisted column (no migration needed, and "first unanswered" is a reasonable, simple resume point). `EnvelopeResponse` gained `timeSpentSeconds` (`envelope.ts`, sourced from `attempt_response.time_spent_seconds`, already persisted but never returned before). `TestTakingView.tsx`'s `selectedAnswers`/`flaggedQuestions`/`questionTimeMap`/`currentIndex` are now all seeded from `session.responses` via lazy `useState` initializers, plus a resync effect keyed on `attemptId` for the case where the component stays mounted across a resume into a different attempt. New Vitest cases in `TestTakingView.test.tsx`: one confirms landing on the first unanswered question with the palette reflecting a restored answered+flagged question (asserted via the always-rendered palette grid rather than navigating through an AnimatePresence transition, which proved timing-flaky under fake timers across the full test file — not the production code's fault, a test-design lesson); another confirms an all-answered resume lands on question 1, not out of bounds. Verified: `tsc` clean; full Vitest suite 36/36 (up from 34) across 3 consecutive runs with no flakes; full node:test backend suite 78/78; production build clean.

### C5 — Double submit
**Severity:** Not reproduced — confirmed idempotent.
**Finding:** `submitAttempt` takes `select ... for update` on the attempt row (`attempt-flow.ts:530`) and short-circuits to an idempotent return if already `scored` (lines 535-557), independent of the optional idempotency-key layer (which adds exact-response replay on top, for retried requests that want the identical HTTP body back). Safe by construction.

**Finding:** Same row lock as C5 serializes a student-triggered submit against a sweeper-triggered one on the same `attempt_id`; further backstopped by `uq_scorecard_attempt_id` (`004_assess.sql:158`) against a double-insert even if the state check were somehow bypassed. **Caveat:** this analysis assumes the sweeper fix from C3 reuses `submitAttempt`/`enforceExpiry` rather than writing its own scoring path — verify this explicitly when C3 is implemented, don't assume it stays true if the sweeper is built as new code.

### C7 — Network drop mid-answer
**Severity:** Not reproduced — confirmed queued, not lost.
**Finding:** `flushDirty` (`TestTakingView.tsx:106-128`) re-queues failed-save question ids into a dirty set for retry on the next periodic interval (12s, line 37) — no permanent loss unless the tab/process itself dies before a successful retry (in which case B7's `beforeunload` guard becomes the mitigation, not this mechanism).

### C8 — Attempt stuck IN_PROGRESS blocks starting a new test
**Severity:** Not reproduced as a standalone bug — mitigated by an existing call, but fragile.
**Finding:** `startAttempt` calls `reconcileUserAttempts(userId)` (`attempt-flow.ts:126`) *before* the active-attempt check — so the very act of trying to start a new test naturally reconciles (and expiry-closes) any stale attempt first, unblocking the user in the same request. **This only works because the reconciliation trigger and the block-check happen to live in the same function.** If C1's `abandoned` state work or C3's sweeper wiring changes this ordering, re-verify this still holds — it's currently correct by construction, not by an explicit guarantee.

## D. NEET blueprint and weightage

### D1 — Blueprint applied at subject level only; unit weightage ignored
**Severity:** P1
**Finding:** Confirmed. Full-mock assembly (`backend/src/controllers/sessionController.ts`) builds exactly one `test_blueprint` line per subject with a flat `pickCount = FULL_MOCK_QUESTIONS_PER_SUBJECT` (hardcoded `45`) and no node targeting at all — a "full mock" is a random 45-per-subject draw, not an NTA-shaped paper with the real per-unit question distribution.
**Root cause:** `catalog.node_weightage` — the table that has exactly the right shape for this (`pattern_id, node_id, weight_marks, expected_questions, priority_rank`, `001_catalog.sql:143-153`) — is fully migrated and CRUD-wired but **never read by `assemble.ts` or `candidate-pool.sql`** (confirmed zero references). It's a complete, connected-nowhere table.
**Affected files:** `backend/src/controllers/sessionController.ts`, `db/assess/test/generation/assemble.ts`, `catalog.node_weightage`.
**Proposed fix:** see §4 "Blueprint work" fix-phase plan — generate one `test_blueprint` line per unit (sourced from `node_weightage`) instead of one per subject, with a tolerance band (D3) and a deviation report (D4). This is the largest single fix in the Fix phase.
**Blast radius:** `sessionController.ts`'s `toLines()` full-mock branch, `assemble.ts`'s line-processing loop (needs to solve across many more lines per test), new versioned blueprint tables per the prompt's schema (`blueprint`, `blueprint_section`, `blueprint_weight` with `effective_from`).

### D2 — Weightage hardcoded in application code instead of a versioned table
**Severity:** P1
**Finding:** Confirmed, and worse than a single hardcode — **two independent, unsynchronized representations exist**: (1) `catalog.node_weightage`, a real table that's simply never consulted (D1), and (2) `frontend/src/data/syllabusData.ts:1-38`, a static 38-unit hardcoded array (`weightageMarks`, `expectedQuestions`, `weightagePercent` per unit) used for syllabus/study-plan display only, with zero connection to either `node_weightage` or test assembly. If either is ever updated, the other silently drifts.
**Affected files:** `frontend/src/data/syllabusData.ts`, `catalog.node_weightage`.
**Proposed fix:** Per the prompt's fix-phase instruction, move weightage into a single versioned source of truth (`blueprint_weight` with `effective_from`, sourced and cited against the official NTA bulletin — not the model's memory, not coaching-site reproductions). Once that exists, `syllabusData.ts`'s display array should read from the same source (via an API) rather than maintaining its own copy — this is the one place in this pass where a small amount of "connect the display to the real data" work is justified, since the alternative is leaving a second permanently-driftable copy in place.
**Blast radius:** New migration + data-seeding (with cited source) + a read path for the frontend display array. Out-of-scope note: changing how `syllabusData.ts` is *rendered* is UI outside the test player and should not be touched — only how it *sources its numbers*, and only if that's a small, contained change; if it turns out to require touching syllabus-module UI meaningfully, defer that part and flag it rather than drifting into out-of-scope territory.

### D3 — No tolerance model
**Severity:** P1 (currently moot because D1 means there's no unit-level target to tolerate around at all — but a real gap once D1 is fixed)
**Finding:** Since unit-level weightage isn't wired into assembly at all today (D1), there is, by definition, no tolerance model either — there's nothing to be exact or loose about yet. This is not "both bugs exist independently," it's one bug (D1) whose fix must be designed with D3 built in from the start, per the prompt's explicit warning that a blueprint with no bounds is exactly as bad as one that must be hit exactly.
**Proposed fix:** Design D1's fix with a `tolerance_band` (e.g. columns `target_count`, `min_count`, `max_count`, or `target ± tolerance_pct`) from day one on the new `blueprint_weight` table — do not ship an exact-match version first and add tolerance later.

### D4 — No deviation report
**Severity:** P1
**Finding:** Confirmed NOT FOUND — no code anywhere computes or returns "how far off the assembled paper is from the target blueprint." `PoolInsufficientError` reports a per-line shortfall, but nothing aggregates a whole-paper deviation summary, and nothing returns one even on a perfect fit (which the prompt explicitly requires — a deviation report should be emitted every time, not only on failure).
**Proposed fix:** Part of the D1 fix — `assembleForAttempt`'s BLUEPRINT-mode return value should include a per-line and whole-paper deviation object (`requested` vs. `actual` per unit/difficulty/type), persisted alongside the attempt (or at least returned once, in the start-attempt response) so it can be surfaced to the user and to R3's fit-simulation report.
**Blast radius:** `assemble.ts`'s return shape, `attempt-flow.ts`'s `startAttempt` response, a new field on `assess.attempt` or a sibling table to persist it if it needs to survive beyond the initial response.

### D5 — Difficulty distribution and question-type distribution not modelled at all
**Severity:** P1
**Finding:** Confirmed — `assess.test_blueprint.difficulty_band`/`question_format` are each a single optional *exact-match filter* per line (`018_test_engine.sql:88-95`), not a distribution/mix (e.g. "30% easy / 50% medium / 20% hard within this line"). A blueprint line can pin one difficulty and one format, or leave both open, but cannot express a proportional mix within itself.
**Affected files:** `db/migrations/018_test_engine.sql` (`test_blueprint` schema), `db/assess/test/generation/assemble.ts`.
**Proposed fix:** If a genuine within-line mix is required (not just "one line per difficulty band," which is a workable alternative using today's schema — multiple blueprint lines per unit, one per difficulty), this needs a new sub-line concept. Recommend the workaround first (multiple lines per unit/difficulty combination) rather than a schema redesign, since it fits today's model with no migration — flag both options for a product decision rather than picking one unilaterally, since it changes how "one blueprint line" is understood everywhere else in the code (D4's deviation report, D3's tolerance bands) if changed.

### D6 — Marking scheme assumed globally rather than read per exam
**Severity:** Not reproduced — confirmed table-driven, this is a "not a bug" finding.
**Finding:** `catalog.marking_scheme` genuinely stores `correct_marks`/`incorrect_marks`/`unattempted_marks`/`partial_credit_rule`/`numeric_tolerance_pct` per scheme, resolved per-section via `catalog.v_section_marking` (`008_catalog_taxonomy.sql:173-179`) and actually read at both attempt-start and scoring time (`attempt-flow.ts:77-87,601-627`). Not counted as a bug; noted so the fix phase doesn't waste effort "fixing" something that's already correct.
**Related, smaller gap found:** `voidDisposition` is hardcoded to `"EXCLUDED"` at every call site (`attempt-flow.ts:626`) since `marking_scheme` has no column for how voided questions should be handled per scheme — logged as a minor follow-up, not blocking.

**Severity:** P1 — confirmed the second half ("loses spread entirely"), not the first.
**Finding:** SUBJ/UNIT-scoped tests use a single caller-supplied blueprint line scoped to one node (`sessionController.ts:128-154`) — they do **not** inherit the full-paper blueprint (so the first half of the lead doesn't reproduce), but they also have **zero sub-topic spread modeling**: a "unit test" is a flat draw from that node (with `include_descendants`), with no per-sub-topic distribution at all, confirming the lead's second reading.

### E2 — `has_image` set manually and drifting from actual assets — confirmed, with the codebase's own diagnostics as proof
**Severity:** P0 (a drifted flag directly causes E3's live-exam failure mode)
**Finding:** `db/scripts/import/import-content.ts` (the real import path) never references `has_image` at all — grepped, zero matches — so every imported question defaults to `false` regardless of whether an accompanying `content.asset` row is created. The only writer anywhere is a manual script (`db/scripts/manual/verify-image-assets.ts:73`, human-run with `--fix`). **Affected files:** `content.question.has_image` (schema), `db/scripts/import/import-content.ts`.
**Proposed fix:** per the prompt's fix-phase instruction — make `has_image` a **computed column or view**, derived from `content.asset` rows, never manually set. Concretely: either (a) drop the column and replace every reader with a subquery/join against `content.asset`, or (b) keep the column but maintain it via an `AFTER INSERT/DELETE` trigger on `content.asset` so it can never drift by construction. Prefer (a) for a hard guarantee, unless read-performance on a hot path requires the denormalized column, in which case (b) with the trigger as the enforcement mechanism.
**Blast radius:** Every reader of `has_image` (`questionController.ts` and any other query touching it) if approach (a); a new migration + trigger if approach (b). Approach (b) is lower blast radius and is the recommended default unless there's a clear performance reason to fully normalize.
**Fixed and shipped, approach (b) as recommended**: `db/migrations/028_has_image_computed.sql` — a one-time backfill (`update ... where has_image is distinct from exists(...)`, correcting any drift immediately on apply) plus `content.trg_asset_sync_has_image()`, a trigger on `content.asset` (`after insert or delete or update of question_id, target_role`) that recomputes the affected question(s)' `has_image` from scratch on every change, so it can never drift again regardless of write path — including the real import pipeline, which previously never touched it at all. The predicate deliberately mirrors `envelope.ts`'s own real "does this question show an image" ground truth exactly (`content.asset` rows with `target_role in ('stem','option')`, no `asset_type` filter) rather than inventing a stricter definition here that could itself drift from what actually renders during the exam — a `solution`/`hint`/`passage`/`explanation`-role asset must not flip `has_image`, confirmed correct with a live test. **Checked before applying, same discipline as A1's migration**: a live drift-detection query first (zero rows differed — this dev DB's 1400 questions/15 assets were already in sync from a prior manual `--fix` run, so the migration was a pure no-op on data, purely adding the trigger going forward). **Verified live, not just reasoned about**: ran the migration + verify script via `node db/scripts/run-migration.mjs 028_has_image_computed`; separately proved the trigger's actual behavior (insert a stem asset → `has_image` flips true; insert an unrelated solution-role asset → stays true; delete the stem asset → flips back false) via a manual rolled-back transaction against live data, then captured the same three assertions as a permanent automated test, `db/content/has-image-trigger.test.ts` (new — `db/content/` had no test coverage at all before this; added `"db/content/**/*.test.ts"` to `package.json`'s `test:unit` glob so it's actually part of the tracked suite, not a one-off). **Verified**: `npx tsc --noEmit` clean; `npm run test:unit` 89/89 node:test (up from 88) + 44/44 Vitest; `npm run build` clean.

## F. Test types and scoping

### F1 — Scope expansion by node_path prefix can pick up sibling nodes (confirmed via SQL analysis, not yet observed against live data)
**Severity:** P1
**Finding:** `LINE_CANDIDATE_SQL`'s descendant-scope match (`assemble.ts:135-136,162-163`) is:
```sql
sn.node_path like (select target.node_path || '%' from catalog.syllabus_node target where target.node_id = $5::uuid)
```
`node_path` is generated as `'/' || node_code` per level (`008_catalog_taxonomy.sql:125-127`), with **no trailing delimiter appended before the `%` wildcard**. If two sibling nodes' `node_code`s share a common prefix (e.g. `U1` and `U10`, or `TOPIC2` and `TOPIC20`), matching `target.node_path || '%'` (e.g. `/PHY/U1%`) will also match the sibling's path (`/PHY/U10`), not just true descendants (`/PHY/U1/...`). This is a genuine SQL pattern defect, independent of whether today's actual `node_code` values happen to trigger it — it will silently start expanding scope incorrectly the moment any sibling code shares a prefix with another.
**Affected files:** `db/assess/test/generation/assemble.ts` (both `LINE_CANDIDATE_SQL` and `LINE_AVAILABLE_SQL` share this pattern).
**Proposed fix:** Match against `target.node_path || '/%'` (append the path separator before the wildcard) **and** keep `sn.node_path = target.node_path` as a separate exact-match branch for the node itself (since the `/%'` version alone would exclude the target node itself, which the current `or qnm.node_id = $5::uuid` clause already covers separately — verify the fix doesn't double-count via that existing clause). Add a regression test with deliberately prefix-colliding node codes (`U1`/`U10`) to prove the fix.
**Blast radius:** Two SQL string literals in one file; low risk, needs a targeted test since it's easy to get the boundary condition subtly wrong.
**Fixed and shipped exactly as proposed**: both `LINE_CANDIDATE_SQL` and `LINE_AVAILABLE_SQL` (`assemble.ts`) now match `target.node_path || '/%'`; verified the existing `qnm.node_id = $<n>::uuid` OR-branch in both queries already covers the target node itself, so dropping the exact-match case from the LIKE clause doesn't lose it, exactly as the proposed fix anticipated. **New regression test** `db/assess/test/generation/scope-prefix-match.test.ts`: rather than fabricating temporary `catalog.syllabus_node`/`content.question` fixture rows across several NOT-NULL-heavy tables in a shared dev database purely to prove a two-character wildcard change, it runs the exact same pattern construction directly against literal path strings through a real Postgres connection — proves the fixed pattern matches true one- and two-level descendants, excludes a prefix-colliding sibling (`/PHY/U10` against target `/PHY/U1`) and that sibling's own descendants, excludes an unrelated sibling, and excludes the target's own path (intentionally, since that's the other OR-branch's job) — plus a sanity check proving the *old* pattern really did match the colliding sibling, so the test is proven to exercise a real defect, not a pattern that was never actually broken. **Verified live**: ran directly against the dev DB, passing; full regression suite after the change: `npx tsc --noEmit` clean, `npm run test:unit` 84/84 node:test (up from 83) + 44/44 Vitest, `npm run build` clean.
