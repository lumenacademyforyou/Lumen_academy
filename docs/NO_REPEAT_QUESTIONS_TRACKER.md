## Known adaptations from the spec's placeholder SQL to this repo's real schema

The spec's SQL is illustrative (it says so implicitly by using generic names); checked live against `information_schema` before writing anything:
- `catalog.subject` really does have `subject_code` — spec's `s.subject_code` is fine as written.
- There is no `catalog.node` table — it's `catalog.syllabus_node` (`node_id`, `node_code`, `title`), matching every other migration in this repo.
- `content.question` has **no `subject_id` column** — subject is only reachable via `content.question_node_map` → `catalog.syllabus_node.subject_id`, same join `assemble.ts`'s `LINE_CANDIDATE_SQL` already uses. Since a question can map to >1 node (the P0-3 fan-out fact `assemble.ts` already documents), census queries must `count(distinct ...)` and account for a question appearing under more than one subject/unit if it's cross-tagged.
- `v_question_eligibility` (referenced in spec §2.3) does not exist anywhere in this schema (confirmed: zero views reference `content.question` at all). Spec's own instruction was "verify no other view... grep for it" — grepped, nothing to update. Recorded as N/A, not silently skipped.
- Spec's `packages/shared/src/normalizeStem.ts` path doesn't exist in this repo (no monorepo `packages/` dir) — this repo's convention is `db/shared/*.ts` for code shared across the DB layer. Using `db/shared/normalizeStem.ts` instead; only server-side code needs it (ingestion + SQL trigger), not the frontend.
